Vektor Flow guide

Vektor Flow is a compiled language for calculations, data and visual programs. Source describes a flow of typed values; the compiler determines concrete types, shapes, storage and a safe execution plan.

Use this guide for the mental model. Follow the linked pages when you want to write code, inspect exact syntax or verify a measured claim.

Values flowing through scopes

Scopes produce values

VKF is built from values, functions and scopes rather than a large vocabulary of special statements. An indented scope produces its final value, and a complete scope can become a record.

A formula can therefore grow into a process without changing models. A physics step can keep intermediate quantities local and return the next state. A data stage can expose its result without leaking temporary names.

Typed without annotation noise

Every value has a compile-time type. An annotation can state a public contract, but it is not required on every binding, parameter or result when the program already supplies enough evidence.

Inference also covers record fields, vector elements and relationships between fixed shapes. Local calculations stay light while library boundaries can still require an exact type or numeric shape.

Functions flow through vectors

Vector application is a core call rule, not a separate collection framework. A function written for one compatible value may be applied through nested vector layers while preserving the result shape.

An exact container match takes priority. Records and tuples remain atomic. Named indices align matching axes, while unmatched names broadcast.

One calibration can serve a sensor, a row of sensors or a batch. One force law can serve a particle or many particles without separate scalar and array versions.

Change is explicit

Declaring a name and updating an existing name are different operations. A misspelling cannot silently create state, and an ordinary expression cannot conceal reassignment.

VKF is value-oriented rather than purely functional. Aggregate updates can preserve alias identity, and mutable capabilities remain available where their purpose requires them. Change stays marked and scoped.

Control flow uses operators and indentation

Conditions, matching, loops, early return, assertions and typed error handling use operators and indentation. The language has no if, else, while, catch or finally keywords.

Scopes and branches produce values directly. Generated unwinding releases ordinary owned values when a function exits or an error propagates, while effects retain their defined order.

How the compiler settles the flow

The compiler establishes meaning before choosing execution. Overload selection, type and shape inference, vector lifting and ownership are compile-time decisions rather than work left to a dynamic dispatcher.

The main path is VKF source → canonical typed IR → machine IR → target artifact.

  1. The frontend parses scopes and calls, resolves names and overloads, and records exact inferred operations in canonical typed IR.
  2. Lowering makes layouts, ownership transfers, dependencies, effects and error paths explicit in target-neutral machine IR.
  3. Optimisation may specialise calls, remove unreachable work and safe copies, or select proven inlining, fusion, SIMD and parallel plans.
  4. A direct backend writes PE, ELF, Mach-O or WebAssembly artifacts without invoking a separate compiler, assembler or linker for each program.

Concrete facts survive the path. A fixed vector shape can become an exact layout, while a lifted scalar function can become direct calls or a loop rather than runtime type inspection.

Optimisation is evidence-bearing. A candidate must preserve exact output before its receipt is retained, and cached evidence is reused only while the program, dependencies, target, host and toolchain still match.

Lazy and parallel beneath the source

Execution begins with one deterministic serial meaning. Programs do not need worker pools, futures, joins, device objects or chunk sizes for ordinary work.

Where semantics allow it, an implementation may retain demand-backed data, fuse adjacent operations, use SIMD, run independent regions on multiple cores or choose a supported GPU plan.

Scheduling cannot alter observable behavior. Effects commit in order, fallible work preserves error order, and numeric reductions are not reassociated merely to expose more parallel work.

The current implementation is conservative: pipes are eager, not every vector is demand-backed, and automatic parallel execution is limited to supported and verified shapes.

Event and I/O work is explicit

Quantum is for ordinary computation: a vector expression, reduction or simulation law does not acquire a user-managed thread merely because it can be parallelized. The compiler may choose fusion, SIMD, CPU/GPU placement or a parallel schedule while preserving the same deterministic meaning.

Use .concurrent when the program is coordinating external events or isolated work: queue() distributes each item to one receiver, broadcast() gives each subscriber a branch, process(...) starts an isolated ordinary VKF function, and shared(value) keeps bulk state out of message copies. These are communication primitives, not numerical kernel controls. The native examples show a work queue and process and fan-out subscriptions.

Native and WebAssembly compilers

Published native packages cover Windows x64 and Linux x64. They can compile command-line tools, calculations, tests, numerical kernels and native visual programs on the machine where they run.

The WebAssembly package brings the compiler and supported runtime into a browser or another WASM host. Documentation examples compile locally in a disposable worker rather than on a compilation server.

Browser programs receive no direct filesystem, process, network, DOM or localhost access. Visual output crosses a validated compiler-owned interface.
