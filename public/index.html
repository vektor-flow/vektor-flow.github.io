THE PROBLEM BEHIND THE LANGUAGE

More time investigating.
Less time assembling the tools.

In experimental research, an interesting pattern often starts with a small question about a large dataset. Investigating it can mean loading more data than you need, adapting a function to another axis, arranging parallel workers and wiring together different plotting tools.

VKF’s answer is a connected language design: request the values you need, express dimensions directly, reuse functions naturally and build views from the same data. The goal is a shorter path from a question to understanding—for researchers and anyone who explores data.

How it started: physics, a function parser and a design question

The founder worked as an experimental physicist in quantum materials, exploring heavy datasets and algorithms that made patterns stand out. Memory use, dimension-specific signal processing, parallel infrastructure and plotting plumbing repeatedly interrupted that exploration. Even browsing a stack of 100 images meant building a viewer.

In early 2026, a friendly conversation about a function-parser exercise led to an experiment in Rust. A symbolic parser and evaluator grew into a language as functions became part of an AST; operators and core containers followed, with AI assistance.

One recurring question shaped the grammar: could a coherent, intuitive language work without reserved keywords? The aim remains the language its founder wished had existed during that research.

03 / WHAT THE LANGUAGE GIVES YOU
Design choices with
an everyday purpose.
01 / DEMAND
Ask for a value. Avoid unrelated work.
Language-level demand is the goal. The preview shows finite demand on an unbounded range; arbitrary out-of-core datasets are not yet qualified.
values.(0..3)02 / DIMENSIONS
Say which axes a function should see.
Keep selected dimensions together and lift over the others. Describe the signal-processing operation directly, with fewer reshaping tricks.
span_i(A_ij)03 / FUNCTIONS
Fix one argument. Reuse the idea.
Callbacks and reducers use ordinary function values. Specialization binds named arguments without evaluating the function.
cube:power[n:3]04 / VISUALIZATION
Build views from a consistent model.
Add properties and coordinates to viewport layers, then show the result. The spectral example calculates across sites and plots the selected energy curve.
frame.add(p:p_uc)05 / EXECUTION
Spend less time managing the machinery.
The goal is compiler-chosen CPU or GPU execution where beneficial. Automatic placement is still incomplete; measured results have specific workloads and limits.
See the evidence →06 / GRAMMAR
Keep names available for your ideas.
A grammar without reserved keywords is a guiding design constraint. Expressions and punctuation carry structure; calls and specialization follow consistent rules.
