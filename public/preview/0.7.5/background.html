Why I am building Vektor Flow.

My work in data engineering, visualization and experimental quantum materials has shaped what I want from a scientific programming language.

I work with algorithms for finding patterns in large measurements. Changing an analysis question often meant rebuilding the machinery around it: arranging data access, choosing dimensions, managing parallel work and constructing a view. Vektor Flow brings those concerns into the language so they can be designed together.

Follow a question through the data.

Consider a spectral map with an energy trace at each measurement position. I want to compare the variation in the traces, inspect the spectrum behind an unusual result, then change the transformation or the dimension it acts on. A selected trace should retain its energy coordinates; reducing the energy dimension should leave the measurement positions available for comparison.

Existing tools can express these steps. The problem I want to address is the repeated translation between their interfaces. Named dimensions and dimension-aware function application make the relationship between an analysis and its axes visible in the program.

Ask for the result that is needed.

Memory was a recurring frustration. A calculation that ultimately selects a small result can still materialize much more data along the way. I want selection and evaluation to stay connected across composed operations, while preserving the dependencies of reductions and neighborhood calculations.

General disk-backed evaluation remains a development goal. The current spectral example uses generated data in memory; it demonstrates the analysis workflow without establishing a general disk reader or a memory-saving guarantee.

Reduce the machinery around the calculation.

I built my own worker pools and parallel infrastructure, and spent hours building a viewer to navigate images. Those experiences inform two goals: use the structure of a calculation to guide execution choices, and carry coordinates and computed data into a consistent view vocabulary.

Automatic choices between CPU and GPU execution remain an optimization goal, not a guarantee. The current viewport examples connect calculated coordinate arrays to plots; broader stack navigation is a separate goal. The purpose is to make it easier to change an analysis and inspect the consequences without rebuilding its surrounding tools.

Build the relationships into the language.

The starting point was readability: expressing calculations clearly without keywords. Binding selected arguments to a function was another repeated task I wanted directly in the notation. Together with dimensions, evaluation and views, these concerns explain the decision to build a language.

The existing examples make particular parts of that design available to inspect and use. Larger goals still require implementation and evidence; the library reference describes current support, and Syntax contains the editable programs.
